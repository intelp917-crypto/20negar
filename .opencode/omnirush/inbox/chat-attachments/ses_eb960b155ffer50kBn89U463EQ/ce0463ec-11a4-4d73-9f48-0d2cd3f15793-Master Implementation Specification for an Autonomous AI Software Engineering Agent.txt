# 20Negar Enterprise Modernization
## Master Implementation Specification for an Autonomous AI Software Engineering Agent

**Repository:** `https://github.com/intelp917-crypto/20negar`

**Mission:** Transform the existing 20Negar application into a reliable, high-performance, production-grade media workflow platform for daily organizational use.

**Operating principle:** Inspect first, preserve valuable existing functionality, implement changes incrementally, prove correctness with automated tests, and never sacrifice media integrity or workflow authorization for convenience or raw throughput.

# PART I — MISSION, RESPONSIBILITIES, AND NON-NEGOTIABLE REQUIREMENTS

## 1. Your Role

You are the lead software architect, senior full-stack engineer, storage and transfer engineer, database engineer, security engineer, test engineer, and deployment engineer responsible for modernizing the existing 20Negar repository.

You are expected to execute engineering work, not merely write recommendations or generate a theoretical architecture.

You must:

1. Inspect the entire repository before making architectural decisions.
2. Understand the existing application, database schema, authentication, authorization, upload implementation, storage layout, media processing, and deployment model.
3. Identify existing defects through code inspection and reproducible tests.
4. Produce an implementation plan with explicit dependencies, risks, and acceptance criteria.
5. Implement the approved architecture in the existing repository.
6. Add database migrations, automated tests, operational diagnostics, and recovery mechanisms.
7. Execute available tests, builds, static analysis, security checks, and performance benchmarks.
8. Correct defects discovered during implementation.
9. Update documentation, environment templates, deployment scripts, and recovery procedures.
10. Produce a final implementation report containing actual test results, unresolved limitations, changed files, migration instructions, and deployment instructions.

Do not stop after writing a plan. Continue through implementation and verification whenever the available environment permits.

Do not claim that an operation, test, migration, deployment, or performance target succeeded unless you actually executed it and observed the result.

If an operation cannot be performed because a dependency, credential, external service, operating-system feature, or production environment is unavailable, document the exact blocker and continue with independent work.

## 2. Business Context

20Negar is used to manage original media files and edited deliverables for organizational publishing workflows.

Typical media include:

- Original videos recorded by videographers.
- Original photographs.
- Edited video files.
- Edited photographs and graphics.
- Review and approval records.
- Approved deliverables prepared for publication.
- Files organized by project, client, campaign, and content category.

An example project is:

**Project:** Sepehr Dental Clinic

The project may contain multiple categories, including:

- Raw video footage.
- Original photographs.
- Edited video.
- Edited photographs.
- Approved Reels.
- Approved Stories.
- Final Instagram post assets.
- Supporting files and project notes.

The application must make these assets easy to find, transfer, review, approve, and publish without losing original media or allowing unauthorized users to access unpublished material.

The primary operating environment is a single organizational server initially serving approximately ten concurrent users, with possible future growth.

The application must be designed so that it can scale without requiring a complete rewrite, but it must not introduce distributed infrastructure, microservices, message brokers, or complex orchestration unless measurable requirements justify them.

## 3. Priority Order

Treat these requirements in the following order:

1. **Media integrity and prevention of unauthorized publication.**
2. Correct workflow transitions and role-based authorization.
3. Durable storage, recoverability, and database consistency.
4. Correct upload and download behavior under interruptions.
5. High transfer throughput on the local network.
6. Responsive application navigation and low-latency user interactions.
7. Operational simplicity, maintainability, and future scalability.

Performance optimizations must never silently bypass the higher-priority requirements.

## 4. Non-Negotiable Rules

### 4.1 Preserve original media bytes

The original file must be preserved byte-for-byte.

Do not transcode, recompress, resize, alter metadata, normalize, or otherwise modify an original file during upload or ordinary storage.

Do not use a media-processing pipeline as part of the original upload path.

Thumbnails, previews, proxies, transcoded videos, and HLS renditions must be stored as separate derived assets linked to the original asset.

### 4.2 Never equate upload success with workflow approval

A completed upload is not an approved deliverable.

A successful media-processing job is not an approved deliverable.

A file being visible to a user does not mean the user can approve it.

Only an explicitly authorized workflow transition may approve content.

### 4.3 Never trust the frontend for authorization

Every protected operation must be authorized on the server.

Hiding a button, disabling a menu item, or removing a page from navigation is not authorization.

### 4.4 Do not discard existing data

Do not delete existing files, replace the production database, remove existing storage directories, or run destructive migrations without a verified backup and an explicit, documented migration procedure.

Never run destructive tests against production data.

### 4.5 Do not invent performance claims

Measure before and after changes.

Record actual throughput, latency, CPU, memory, disk I/O, error rates, and test conditions.

### 4.6 Do not leave parallel implementations indefinitely

If a legacy upload implementation is replaced, establish an explicit compatibility or deprecation policy.

Do not leave several active upload pipelines with conflicting size limits, session models, authorization rules, or finalization behavior.

# PART IV — LOCAL NETWORK MODE: “INTERNAL APP”

## 10. Business Requirement

Add an administrative setting that allows the Super Admin to configure the organization's internal server address.

Every authorized user must have an **Internal App** button in the application interface.

When selected, the application should open or switch to an internal-network application address when that address is reachable and verified.

The goal is to improve upload and download performance when users are connected to the organization's LAN.

The public application must continue to work when users are outside the organization.

The feature must be reliable across multiple devices, browsers, network configurations, and application restarts.

## 11. Super Admin Configuration

Add an administration section named:

**Network and Internal Access**

It must support configuration of:

- Internal application hostname or IP address.
- Internal HTTPS port.
- Optional internal application base path.
- Internal application enabled/disabled state.
- Internal endpoint health status.
- Last successful health check.
- Connection instructions for users.
- A safe verification action.

Example configuration:

```text
Internal application:
https://192.168.1.20:3000
```

This is an example only. Never hardcode it as a real organizational address.

Prefer a stable internal DNS hostname and a trusted HTTPS certificate when the organization's infrastructure supports them.

If a literal IP address is required, document certificate trust requirements and the consequences of IP changes.

Validate the configured value on the server.

Accept only supported schemes and ports.

Reject credentials embedded in URLs, unsupported schemes, malformed addresses, and unsafe paths.

Do not allow arbitrary external URLs to be configured as internal endpoints.

Store the configuration in the existing database or a suitable protected configuration store.

Do not expose administrative configuration secrets to ordinary users.

## 12. Important Browser and Network Constraints

An application cannot reliably switch its own network route merely by changing a hostname in JavaScript.

Browser security rules, DNS resolution, TLS certificate validation, CORS, cookies, mixed-content policies, and network reachability all affect whether the internal endpoint works.

The agent must explicitly account for these constraints.

### 12.1 Prefer one logical origin when possible

Evaluate whether the internal and external entry points can share the same application origin from the browser's perspective through an appropriately configured reverse proxy, split-horizon DNS, or another supported network design.

Do not assume that an internal IP can reuse the public origin's cookies or TLS identity.

### 12.2 Do not silently downgrade security

Never switch from HTTPS to HTTP simply because the internal HTTPS endpoint is unavailable.

Do not send credentials, JWTs, session cookies, or sensitive upload metadata to an unverified destination.

### 12.3 Health verification

Implement a small, authenticated or appropriately scoped health endpoint.

The endpoint must report only minimal operational information.

It must not reveal filesystem paths, environment variables, secrets, database credentials, or internal diagnostics to unauthenticated callers.

Before switching to internal mode, verify:

- The endpoint is reachable.
- TLS validation succeeds.
- The endpoint identifies itself as the expected application.
- The user can authenticate through the intended mechanism.
- The required upload and download routes are available.

A failed health check must not disable the external application.

### 12.4 User interface behavior

The Internal App button must show a clear state:

- Internal access available.
- Internal access unavailable.
- Switching to internal access.
- Currently using internal access.
- Returned to external access.

Do not display a success state until the destination is verified and navigation or connection has actually succeeded.

If switching requires a page reload, explain that behavior in the interface.

Preserve unsaved work and active upload sessions when practical.

## 13. Internal and External Access Must Share the Same Data

The internal and external entry points must operate on the same authoritative backend data and media storage.

Do not create a separate internal database.

Do not duplicate the media library merely to support LAN access.

Do not let the internal path bypass the normal authorization or audit layers.

Internal access may use a different network path, but it must not create a second set of business rules.

## 14. Network Security

The default recommended topology is:

- External users connect through the public HTTPS entry point.
- Internal users connect through the verified internal HTTPS entry point.
- Both entry points reach the same application services.
- The database is not directly exposed to client devices.
- The Rust transfer service, if retained, is not publicly accessible unless a separately reviewed design explicitly requires it.
- Internal network access is not automatically trusted as user authorization.

If the existing application uses JWT authentication, preserve its intended authentication semantics and review token storage and transport.

If the internal and external origins differ, implement an explicit session or token strategy compatible with browser security rules.

Do not place long-lived bearer tokens in query strings.

Do not expose authentication tokens through logs, analytics, browser history, or referrer headers.

## 15. Internal Mode Acceptance Criteria

The feature is not complete until the following scenarios are tested:

1. Internal mode works on a supported device connected to the LAN.
2. External mode works from outside the LAN.
3. An unavailable internal endpoint produces a clear error and preserves external access.
4. Invalid certificates are rejected.
5. Changing the configured internal address takes effect predictably.
6. An ordinary user cannot modify the configuration.
7. The internal route enforces the same permissions as the external route.
8. Upload sessions can be resumed using the supported application workflow.
9. A user cannot use the internal mode to download a file they are not authorized to access.
10. No secrets are exposed by the health endpoint.

Measure internal throughput separately from external throughput.

Do not claim that switching to internal mode improves speed unless benchmarks confirm the improvement.

The Videographer must not publish media.

The Videographer must not silently overwrite an existing original asset.

### 16.3. Editor

Editors receive access to newly uploaded original material, prepare edited assets, and submit deliverables for technical review.

**Important exception: every active Editor must be able to see newly uploaded original media at the initial stage, as explicitly required by the business.**

This exception means all active Editors can discover the relevant original assets according to the organization's shared-workspace policy. It does not mean every Editor may access every restricted project or bypass confidentiality rules.

Implement this as an explicit permission policy rather than an accidental consequence of frontend filtering.

Capabilities:

- View shared original-media queues.
- View originals for projects to which the Editor is entitled.
- Download authorized original files.
- Create edited deliverables.
- Upload edited videos, photographs, and graphics.
- Associate each edited deliverable with its source media.
- Add revision notes.
- Submit deliverables for technical review.
- View review results and requested corrections.
- Upload new revisions without overwriting previous review evidence.

Editors must not approve their own submissions unless a separately approved organizational policy explicitly authorizes that exception.

Editors must not publish unapproved deliverables.

### 16.4. Technical Supervisor

The Technical Supervisor reviews submitted edited deliverables.

Capabilities:

- View the technical-review queue.
- Preview or download authorized deliverables.
- Compare revisions.
- Review source-media references.
- Inspect media metadata and integrity information.
- Approve a revision.
- Reject a revision with a mandatory reason.
- Request changes.
- Record technical notes.
- View approval history.

Approval must apply to a specific immutable revision, not merely to a filename or mutable asset record.

The Supervisor must not approve a revision that has changed after review.

If a new revision is uploaded, prior approval must not silently transfer to the new revision.

### 16.5. Publishing Admin / Destination Manager

The Publishing Admin is responsible for assigning approved deliverables to their publication destination.

Capabilities:

- Assign the responsible publishing user.
- Define relevant publication metadata.

- View the publication queue.

The Publishing Admin must not approve a technically rejected deliverable.

### 16.6. Publisher / Destination User

The Publisher receives the approved files assigned to them and downloads the files for publication, such as uploading content to Instagram.

Capabilities:

- View deliverables explicitly assigned to them.
- Download authorized original or final assets.
- View publication instructions.
- Record download completion.
- Mark a publication as published, failed, or cancelled.
- Record the publication URL and relevant timestamp.
- View the approval record associated with the deliverable.

The Publisher must not edit the approved file in place.

If the Publisher modifies an asset and needs the modified version to become the official deliverable, the modified file must enter the appropriate revision and approval process.

## 17. Model Permissions Explicitly

Create a permission matrix and implement server-side checks for every protected operation.

Do not rely exclusively on a simple role-name check when project membership, asset ownership, workflow state, or destination assignment also matters.

The effective permission decision should consider:

- User identity.
- Active account status.
- Role.
- Project membership.
- Asset visibility policy.
- Asset ownership where applicable.
- Current workflow state.
- Revision identity.
- Destination assignment.
- Operation being requested.

Implement a centralized authorization policy or a small, well-defined set of policy services.

Do not scatter inconsistent role checks across route handlers.

Create automated authorization tests for both permitted and forbidden actions.

## 18. Required Workflow

Implement the following default workflow.

### Stage A — Original Media Collection

1. A Videographer records video and photographs.
2. The Videographer creates or selects an authorized project.
3. The Videographer uploads original media.
4. The system verifies that each upload is complete and intact.
5. The system records the original asset and its immutable revision.
6. The original media becomes visible to authorized Editors through the shared original-media policy.
7. The asset remains in the original-media state until an authorized workflow transition occurs.

Original assets must remain unchanged.

An original asset must not become an approved publishing asset simply because it has been uploaded.

### Stage B — Editing

1. An Editor selects an original asset or group of related assets.
2. The Editor downloads the authorized source files.
3. The Editor performs the required editing outside the platform or using an approved integrated tool.
4. The Editor uploads the edited deliverable.
5. The Editor links the deliverable to the relevant project and source assets.
6. The Editor supplies a revision identifier, notes, and relevant media metadata.
7. The Editor submits the deliverable for technical review.

The system must preserve the relationship between source media and edited deliverables.

A deliverable may reference multiple source files.

An original asset may have multiple edited derivatives.

Do not assume that one source video always maps to one final video.

### Stage C — Technical Review

1. The submitted deliverable enters the technical-review queue.
2. The Technical Supervisor receives an appropriate notification.
3. The Supervisor opens the exact submitted revision.
4. The Supervisor reviews the file and its relevant metadata.
5. The Supervisor approves the revision, rejects it, or requests changes.
6. The system records the actor, timestamp, decision, revision ID, and reason.
7. If changes are requested, the Editor uploads a new revision.
8. The new revision returns to technical review.

Approval must be bound to the reviewed revision's stable ID and verified checksum.

Do not allow an approval record to point ambiguously to a filename that may later contain different bytes.

### Stage D — Destination Assignment

1. Only an approved revision can enter the publishing-assignment queue.
2. The Publishing Admin selects an authorized destination.
3. The Publishing Admin assigns a Publisher or responsible account.
4. The system records the approved revision, destination, assignment, and publication instructions.
5. The Publisher gains access to the assigned deliverable.

The assignment operation must verify the current approved revision again on the server.

### Stage E — Download and Publication

1. The Publisher opens their assigned items.
2. The Publisher downloads the authorized approved revision.
3. The server records the download event where appropriate.
4. The Publisher publishes the file using the intended external platform.
5. The Publisher records the publication outcome and URL.
6. The system retains the audit history.

Do not claim that content has been published merely because it has been downloaded.

Actual Instagram publishing integration is outside the minimum scope unless the repository already contains a supported integration and its requirements are separately verified.

## 19. Workflow State Machine

Implement a formal state machine rather than loosely coupled booleans.

A possible default lifecycle is:

```text
ORIGINAL_UPLOADING
    |
    v
ORIGINAL_AVAILABLE
    |
    v
EDITING
    |
    v
SUBMITTED_FOR_REVIEW
    |
    +---- changes requested ----> REVISION_REQUIRED
    |                                 |
    |                                 v
    |                           EDITING
    |
    +---- rejected ----------------> REJECTED
    |
    +---- approved ---------------> APPROVED
                                      |
                                      v
                              DESTINATION_ASSIGNED
                                      |
                                      v
                              READY_FOR_DOWNLOAD
                                      |
                                      v
                               DOWNLOADED
                                      |
                                      v
                               PUBLISHED
```

This is a logical reference model, not a requirement to represent all states in one database column.

Model upload state, review state, assignment state, and publication state separately when they have independent lifecycles.

For example, upload completion and video transcoding status must not be conflated.

Define all allowed transitions explicitly.

For every transition, specify:

- Permitted roles.
- Required project access.
- Required source state.
- Required target state.
- Required metadata.
- Revision immutability rules.
- Audit event.
- Notifications.
- Failure behavior.
- Idempotency behavior.

Reject invalid transitions on the server.

Do not permit a request to set an arbitrary status value directly.

## 20. Immutable Revision and Approval Rules

Every submitted deliverable must have an immutable revision identity.

At minimum, store:

- Asset ID.
- Revision ID.
- Parent or source asset IDs.
- Storage key.
- File size.
- SHA-256 checksum.
- Creation timestamp.
- Creator.
- Revision notes.
- Review state.
- Approval record, if applicable.

Once a revision is submitted for review, its bytes must not be overwritten in place.

If the same logical asset is edited again, create a new revision.

If the bytes of a previously approved revision are found to differ from its recorded checksum, mark the integrity condition as a critical incident, prevent further publication or download where appropriate, and trigger investigation.

Do not silently invalidate the evidence or replace the approved file.

# PART VII — MEDIA INTEGRITY AND STORAGE

## 25. Absolute Media Integrity Requirement

The platform must preserve uploaded original files byte-for-byte.

A file transferred in chunks is not inherently modified by chunking.

Splitting a byte stream into chunks, transmitting the chunks, and reconstructing them in the correct order preserves the original bytes when implemented correctly.

The following are acceptable:

- Chunked uploads.
- Resumable uploads.
- Parallel transfer of independent, correctly addressed byte ranges.
- Streaming uploads.
- Streaming downloads.
- HTTP Range downloads.
- Hash-based integrity verification.
- Separate thumbnail generation.
- Separate transcoded derivatives.

The following are prohibited in the original-media path:

- Re-encoding the original video.
- Recompressing original photographs.
- Resizing original images.
- Replacing the original with a preview.
- Lossy conversion during storage.
- Silently modifying orientation or metadata.
- Reconstructing files using incorrect offsets.
- Publishing an incomplete file.
- Overwriting a previously approved revision.

## 26. Checksum Strategy

Use SHA-256 for integrity verification.

Record the expected size and, when available, a client-provided checksum.

Do not trust a client-provided checksum as proof of integrity.

The server must calculate or verify the final checksum from the actual completed file.

For resumable uploads, a full-file SHA-256 calculation can be performed after completion without keeping the entire file in memory.

Stream the file through the hashing implementation.

For very large files, avoid allocating a buffer proportional to file size.

Record:

- Expected size.
- Actual size.
- Final SHA-256.
- Upload session ID.
- Storage key.
- Verification timestamp.
- Verification result.

A failed integrity check must prevent finalization.

## 27. Storage Architecture

Separate logical metadata from physical storage.

Use generated storage keys rather than trusting filenames or user-supplied paths.

Keep temporary uploads outside any publicly served static directory.

Only authorized download endpoints may expose protected media.

The storage service must support:

- Creating temporary upload files.
- Appending or writing validated ranges.
- Verifying file size.
- Calculating checksums.
- Moving completed files.
- Deleting expired temporary files.
- Checking free disk capacity.
- Detecting missing files.
- Detecting orphaned files.
- Recovering incomplete finalization.
- Reporting storage errors.

Do not implement filesystem operations directly in unrelated HTTP handlers.

## 28. Safe Finalization

Database transactions and filesystem operations do not form one atomic transaction.

Design finalization as a recoverable state machine.

For example:

1. Validate the completed upload session.
2. Verify expected and actual size.
3. Verify the file checksum.
4. Persist the session's finalization intent.
5. Move the file to its final location using an atomic rename when source and destination are on the same filesystem.
6. Persist the asset and revision records.
7. Mark the upload session complete.
8. Emit the appropriate audit event.
9. Schedule derived-media processing separately.

Adapt the exact order to the existing database schema and the selected storage implementation.

The implementation must recover safely from a crash between every pair of steps.

Use a durable recovery worker to identify and resolve or quarantine incomplete finalization states.

Finalization must be idempotent.

Repeated finalization requests must not create duplicate assets or corrupt workflow state.

## 29. Cross-Filesystem Transfers

An atomic rename cannot generally be assumed across different filesystems.

When the temporary and final locations are on different filesystems:

1. Copy to a temporary destination file.
2. Verify the copied size.
3. Verify the copied checksum.
4. Flush data as required by the durability policy.
5. Rename the temporary destination into its final destination on that filesystem.
6. Persist the resulting storage state.
7. Delete the original temporary file only after successful completion and verification.

Do not delete the only valid copy before the destination is confirmed.

## 30. Disk Capacity and Quotas

Centralize upload policy configuration.

The initial target should support files of approximately 20 GiB, with a configurable maximum that provides reasonable headroom.

A possible starting configuration is:

```dotenv
MAX_UPLOAD_BYTES=26843545600
UPLOAD_SESSION_TTL_HOURS=72
MAX_CONCURRENT_UPLOADS_PER_USER=3
```

These are initial design values, not universally correct production settings.

Tune them through actual measurements and operational policy.

The application must distinguish decimal GB from binary GiB in its interface and documentation.

Check available capacity before accepting a large upload, but recognize that free-space checks are advisory because other processes may consume disk space later.

Handle disk-full errors during every write and finalization step.

Implement per-user and global limits for active upload sessions and temporary storage.

Do not allow an authenticated user to exhaust the server's disk by creating unlimited incomplete sessions.

# PART VIII — UPLOAD PIPELINE REDESIGN

## 31. Primary Objective

Create one authoritative, resumable upload workflow.

Do not keep multiple independent implementations as active primary paths.

Evaluate the existing TUS implementation and Rust transfer service before selecting the final transport architecture.

Do not assume that replacing all custom code with a new library is automatically safer.

Choose the simplest implementation that meets the required integrity, resume, throughput, observability, and recovery requirements.

## 32. Recommended Starting Point

For the initial production implementation, prefer the existing TUS integration if the repository audit confirms that it can be correctly installed, secured, configured, and tested.

Use the existing Rust transfer implementation only if it passes the same acceptance criteria and its additional complexity provides a measurable benefit.

Do not maintain two unrelated upload session models.

Do not silently restart an upload through a second protocol after partial progress unless the transition explicitly maps to a verified compatible session.

A failed fast path must not create untracked temporary files or leave ambiguous session state.

## 33. Upload Session Model

Create a durable upload session containing at least:

- Stable upload ID.
- Owner user ID.
- Project ID.
- Optional source or parent asset ID.
- Original filename.
- Expected size.
- Actual received size or protocol Offset.
- Declared media type.
- Verified media type, where applicable.
- Temporary storage key.
- Final storage key, when assigned.
- Session state.
- Created timestamp.
- Updated timestamp.
- Expiration timestamp.
- Final checksum.
- Error code and safe diagnostic details.
- Finalized asset or revision ID, when applicable.

The database must be the authoritative source for session ownership and workflow state.

The transfer protocol may maintain additional protocol-specific state, but it must remain consistent with the application's durable session record.

## 34. Upload API Contract

Design a documented upload API with explicit semantics.

A possible interface is:

```text
POST   /api/uploads
HEAD   /api/uploads/{uploadId}
PATCH  /api/uploads/{uploadId}
GET    /api/uploads/{uploadId}
POST   /api/uploads/{uploadId}/finalize
DELETE /api/uploads/{uploadId}
```

Adapt these routes to the selected TUS version and the existing routing conventions.

Do not implement a superficially similar custom protocol and call it TUS.

If the selected TUS library requires protocol-specific routes, use those routes and document how they map to the application upload session.

Every request must verify authentication, authorization, upload ownership, session state, and size constraints.

Use correct protocol response codes and headers.

Reject conflicting offsets rather than silently appending data at the wrong position.

## 35. Resume Semantics

Resume must work across:

- Temporary network interruptions.
- Browser refresh.
- Browser closure and reopening where session recovery is supported.
- Application server restart.
- Temporary transfer-service restart.
- Retry after a transient HTTP failure.

The client must recover the correct session ID and query the authoritative transfer Offset.

Do not assume that a locally stored progress percentage is authoritative.

The server's durable state determines the valid resume point.

Persist session references on the client in a way that does not expose bearer tokens or grant access independently of server-side authorization.

On resume, revalidate the current user and session ownership.

If a session cannot be resumed safely, provide a clear error and a safe restart option.

## 36. Chunk Size and Parallelism

Do not optimize chunk size based on intuition alone.

Benchmark representative values such as:

- 4 MiB.
- 8 MiB.
- 16 MiB.
- 32 MiB.

These are benchmark candidates, not mandatory production defaults.

Measure:

- Sustained throughput.
- Number of requests.
- CPU consumption.
- Memory consumption.
- Disk write behavior.
- Retry overhead.
- Performance under packet loss or latency.
- Resume overhead.
- Behavior under multiple concurrent uploads.

Start with a simple, reliable configuration.

Enable parallel chunk transfer only if the selected protocol and implementation support it correctly and benchmarks show a measurable benefit.

Never allow two writers to corrupt the same logical byte range.

Ensure concurrent session updates cannot lose metadata updates.

## 37. Retry Policy

Implement bounded, observable retries for transient errors.

Use exponential backoff with jitter for retryable network and server errors.

Honor server-provided retry instructions where applicable.

Do not retry permanent errors indefinitely.

Examples of non-retryable conditions include:

- Unauthorized access.
- Forbidden project access.
- Invalid upload size.
- Unsupported request format.
- Expired or revoked session.
- Invalid Offset.
- Failed final integrity validation.

Provide an explicit Cancel action.

Cancellation must stop future transfer work and update the session state safely.

Do not delete completed files or valid prior assets when cancelling an unrelated upload.

## 38. Upload Progress

Progress must distinguish:

- Bytes transferred by the browser.
- Bytes acknowledged by the server.
- Verified bytes.
- Finalization status.
- Post-upload processing status.

Do not show 100% completion merely because the browser has transmitted the last request.

The UI should indicate that transfer is complete but integrity verification or finalization is still running.

Use the protocol's acknowledged progress where available.

Do not calculate progress from an assumed chunk count if the server reports a different Offset.

## 39. Cancellation and Cleanup

Cancellation must be idempotent.

Define whether cancellation means:

- Stop transfer while retaining a resumable session.
- Permanently abandon a session and schedule cleanup.
- Cancel post-upload processing.
- Cancel a user-visible task without deleting the underlying completed asset.

These are different operations and must not share ambiguous semantics.

Expired-session cleanup must:

1. Find expired sessions.
2. Confirm that they are not being actively finalized.
3. Acquire the appropriate session-level lock or transactional claim.
4. Delete only the associated temporary files.
5. Record cleanup results.
6. Preserve completed assets and audit records.
7. Retry safely after errors.

Never delete files by matching an untrusted filename pattern.

# PART IX — DOWNLOAD PERFORMANCE AND INTEGRITY

## 40. Download Requirements

Implement efficient downloads for original videos, photographs, edited deliverables, and approved revisions.

Use streaming rather than loading full files into application memory.

Support appropriate HTTP semantics:

- `Content-Length`.
- `Content-Type`.
- `Content-Disposition`.
- `ETag` or a suitable strong validator.
- `Last-Modified` where appropriate.
- HTTP Range requests.
- `206 Partial Content`.
- `416 Range Not Satisfiable`.
- Conditional requests where supported.

Verify that Range requests return the exact requested bytes.

Do not claim support for multipart ranges unless the implementation actually supports them.

Use a stable file revision or checksum to derive validators.

A download must refer to an immutable asset revision.

If the underlying bytes change, do not reuse an ETag that incorrectly identifies the new content as the old version.

## 41. Authorization Before Streaming

Authorize the user before exposing file bytes.

For protected media, do not place files in a public directory and rely on obscurity of the URL.

Do not treat an unguessable storage key as a substitute for access control.

Ensure that partial downloads and resumed downloads use the same authorization policy as full downloads.

When a user loses access, subsequent requests must not continue receiving protected content through an unprotected download route.

## 42. Local-Network Download Optimization

When users are on the LAN, the internal endpoint should serve the same immutable bytes through the verified internal path.

Do not add an unnecessary server-to-server copy between the internal and external entry points.

Do not proxy a large file through a memory buffer.

Prefer efficient filesystem streaming and correct backpressure handling.

Measure actual network, disk, and CPU bottlenecks before adding Rust, native code, worker threads, or a separate transfer daemon.

If a dedicated transfer process is retained, define:

- Its authenticated API.
- Its permitted storage root.
- Its process supervision.
- Its resource limits.
- Its shutdown behavior.
- Its logging.
- Its health checks.
- Its version compatibility with the main application.

- Concurrent finalization jobs.
- Background processing jobs.

## 46. Error Recovery and Notifications

Each task must have a persistent identity.

Use appropriate polling, Server-Sent Events, or WebSockets only where they provide a meaningful benefit.

Do not add real-time infrastructure without a clear requirement.

Notifications must distinguish between:

- Transfer failure.
- Integrity failure.
- Finalization failure.
- Processing failure.
- Review decision.
- Approval.
- Destination assignment.
- Publication status.

Do not report successful completion before the corresponding server-side operation succeeds.

# PART XI — DATABASE AND MIGRATION STRATEGY

## 47. Database Audit

Inspect the current database implementation and determine how data is read, written, persisted, backed up, and migrated.

If the repository uses `sql.js` and exports the in-memory database to a file, evaluate the risks of:

- Synchronous full-database exports.
- Direct file overwrites.
- Delayed persistence.
- Process termination before persistence.
- Concurrent requests mutating the database.
- Inconsistent schema versions.
- Missing transaction boundaries.
- Database corruption recovery.

Do not infer that the existing implementation is broken in every scenario. Demonstrate the relevant failure modes through code inspection and tests.

## 48. Initial Database Recommendation

For the current single-server deployment, evaluate migration to native SQLite using a stable, supported Node.js binding such as `better-sqlite3`.

Retain the existing schema wherever practical.

Do not migrate to PostgreSQL merely because the application is organizational.

Consider PostgreSQL if measured concurrency, multiple application servers, centralized multi-site access, or operational requirements justify it.

Do not introduce PostgreSQL, Redis, object storage, a message broker, or a distributed job system without an explicit architectural reason.

## 49. Database Requirements

Implement:

- Versioned migrations.
- Foreign-key enforcement.
- Appropriate unique constraints.
- Transactions for logically related database changes.
- Short transaction durations.
- Explicit handling of lock contention.
- Query indexes based on actual access patterns.
- Safe parameterized queries.
- Consistent timestamp conventions.
- Audit history for privileged operations.
- Recovery procedures.
- Automated database integrity checks.

Evaluate SQLite WAL and synchronous settings based on durability requirements and actual filesystem behavior.

Do not claim that WAL provides unrestricted concurrent writes.

Do not use one long database transaction while transmitting a large file.

## 50. Migration Safety

The migration must be repeatable or safely resumable.

Before migration:

1. Stop writers to the source database.
2. Create a verified backup.
3. Record source schema and row counts.
4. Run integrity checks where supported.
5. Export or inspect the schema.
6. Test the migration on a copy.

After migration:

1. Verify schema version.
2. Verify table and row counts.
3. Verify critical relationships.
4. Verify users, roles, projects, media records, and audit history.
5. Verify that storage keys still resolve.
6. Execute application integration tests.
7. Test backup restoration.
8. Document rollback limitations.

Do not run two independent database engines that write the same database file.

If rollback would require reverse migration, data transformation, or restoring a backup, document that explicitly.
